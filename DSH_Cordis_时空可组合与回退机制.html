时空可组合与回退机制

从“插件如何加载”走向“运行环境如何动态变化”：理解 Temporal Composition、Spatial Composition，以及 Effect、Context、Session 和 Workspace 层面的回退边界。

核心概念时间可组合空间可组合回退机制生产场景边界与误区总结

01 · 先建立整体心智模型

Cordis 关注的是：运行时组件如何在动态环境中组合、响应变化，并在退出时清理自己造成的影响。

时间维度

Temporal Composition

组件什么时候进入、什么时候退出？进入时做出的修改，退出时如何撤销？

关键词：Effect、Disposer、生命周期、卸载、热更新。

空间维度

Spatial Composition

组件处于哪个运行环境？需要哪些服务？依赖出现、消失或替换时，组件如何响应？

关键词：Context、依赖注入、服务解析、激活条件、作用域。

一句话：时间可组合解决“进出时如何管理变化”；空间可组合解决“在什么环境、依赖什么才能运行”。回退则要进一步区分运行时清理、会话上下文恢复和文件工作区恢复。

一个直观类比

把 Agent 运行环境想象成一个可动态调整的工作团队：新成员加入时带来工具和流程；成员离开时应收回其注册的资源；团队结构变化时，依赖该成员的工作单元需要重新评估；如果某次工作做错，还要分别考虑撤销流程配置、回到某个讨论节点，或恢复被改动的文件。

02 · 时间可组合：进入时产生影响，退出时能够撤销

问题从哪里来：副作用残留

插件加载时往往不只是“执行一段代码”，还会改变宿主环境。例如注册工具、增加事件监听器、注入服务、修改配置或扩展 Prompt。若插件卸载后这些东西仍留在系统中，就会出现残留状态。

插件加载

  • 注册 search 工具
  • 添加事件监听器
  • 注册服务或命令
产生 Effect

插件卸载

  • 注销 search 工具
  • 移除监听器
  • 撤销服务注册
执行清理

核心机制：Revertible Effects（可逆副作用）

每次执行一个会改变运行环境的操作，同时保留对应的清理动作（常称 disposer）。插件生命周期结束时，运行时可以执行这些清理动作。

// 概念示意：不是对某个 DSH API 的逐字保证
const dispose = registerTool("search", searchHandler);

// 生命周期结束时执行
dispose(); // 注销此前注册的工具
正向 Effect
注册工具 / 服务 / 监听器
↓
保留 Disposer
记录如何撤销此次注册
↓
插件停用或卸载
执行清理动作
↓
运行环境恢复
不留下该插件管理范围内的注册残留

与 try-finally 有什么不同？

传统 try-finally生命周期级可逆 Effect
通常管理一次函数调用或局部资源管理组件/插件生命周期内积累的副作用
清理逻辑通常由调用方组织清理动作可由运行时统一跟踪
作用域较局部可跨越动态加载、停用、卸载和热更新
实际价值：插件可以动态加载、卸载和替换；系统不必因为一个插件变化就重启整个 Agent Runtime。它也是“插件化”能够安全运作的重要基础。

03 · 空间可组合：依赖声明与 Context 作用域

先看依赖问题

假设 Knowledge 插件需要 Database 和 Search 两个服务。传统方式可能要求开发者手工规定启动顺序：先数据库、再搜索、最后知识插件。插件一多，顺序和依赖关系就会变得难以维护。

更合理的方式是让插件声明“我需要什么”，由运行时依据当前环境判断它是否具备激活条件。

// 概念示意：表达依赖声明，不代表精确 API 签名
class KnowledgePlugin {
  static inject = ["database", "search"];

  apply(ctx) {
    // 在依赖可用的 Context 中使用服务
    // 注册 knowledge_search 等能力
  }
}

依赖变化时，组件也要响应

Database + Search 均可用
Knowledge 插件满足依赖条件
↓
Knowledge 插件激活
注册知识检索能力
↓
Database 服务被移除
依赖条件不再满足
↓
Knowledge 插件停用或重新评估
避免继续使用失效依赖
↓
新的 Database 实现出现
依赖重新满足，组件可重新激活

这里表达的是响应式依赖管理的概念流程。具体插件的激活、停用时机和错误处理，取决于 Cordis 的实际依赖声明与生命周期配置。

Context：组件所处的运行环境和作用域

Context 可以理解为一个带层级关系的运行环境。上层 Context 可以提供公共服务；下层 Context 可以继承可见的能力，也可以提供自己的局部实现或配置。

Root Context
公共日志、公共配置、共享服务
↓
Agent A Context
模型 A · 工具集 A · 局部配置
Agent B Context
模型 B · 工具集 B · 局部配置

这让不同 Agent 或任务可以在不同作用域中组合能力，同时复用上层公共服务。服务解析通常遵循 Context 的层级与覆盖规则。

重要边界：Context 隔离是运行时作用域和服务解析层面的隔离，不等同于操作系统进程隔离、容器隔离或安全沙箱。不能仅凭 Context 就推断具备强安全边界。

空间可组合的实际价值

  • 不同 Agent 使用不同模型、工具和配置。
  • 多个插件共享公共能力，但保持各自的局部实现。
  • 依赖可以声明式管理，减少硬编码启动顺序。
  • 服务替换或缺失时，依赖方能够随运行环境变化而调整。

04 · 回退：必须区分三个层次

“回退”不是一个单一按钮。回退什么对象，决定了需要哪种机制。

层次 A

运行时 Effect 回退

对象：插件注册的工具、服务、监听器等。

手段：执行 disposer，清理插件产生的副作用。

目的：插件卸载后不留下受其管理的运行时残留。

层次 B

Session / Context 回退

对象：Agent 可见的会话历史或执行分支。

手段：事件重放、分支（Fork）、视图重建或上下文调整。

目的：从某个历史边界重新探索，不必沿用错误的上下文路径。

层次 C

Workspace 文件回退

对象：Agent 对工作区文件所做的修改。

手段：快照、差异记录、Undo/Redo 或版本控制。

目的：撤销错误代码修改，恢复文件状态。

外部副作用

不自动包含在上述回退中

对象：已发邮件、支付、远程数据库写入、外部 API 操作。

手段：事务、补偿操作、幂等设计或外部系统提供的撤销能力。

目的：处理已经越过本地运行时边界的真实世界影响。

Session 的 Event Sourcing 心智模型

事件溯源的关键是把事件作为历史记录，再由事件构建当前可见的会话状态或消息视图。它与“只保存一份最终对话文本”不同。

user/message
assistant/message
tool/call
tool/result
assistant/message
turn/end

从事件历史可以派生出模型所看到的消息序列。Fork 可以从某个历史边界创建新的执行分支；Replay 可以重新构建历史状态；Compaction 可以压缩模型可见上下文。

关键区别：改变模型后续看到的上下文，不等于删除原始事件；重建 Session，也不等于自动恢复文件系统或外部服务状态。

用 Git 类比，但不要把它们画等号

Git 概念Agent / DSH 中相近的概念区别
提交历史Session 事件历史记录对象和语义不同；Session 事件不一定是代码版本。
创建分支Session Fork分支的是会话/执行历史视图，不必然复制工作区文件。
撤销工作区改动Workspace Undo / Rollback需要快照或文件变更记录支持。
回滚外部系统补偿事务 / 外部撤销 API通常不能靠 Session 回退完成。

05 · 放进一个生产级研发 Agent 场景

任务：开发订单系统的退款功能，并完成测试。Agent 运行环境包含订单服务、支付服务、代码分析工具和测试工具。

初始化插件能力

加载订单、支付、代码分析等插件；各插件注册工具与服务，并建立清理路径。

时间可组合
解析依赖并激活任务 Agent

退款 Agent 声明需要订单服务和支付服务。依赖满足后，在相应 Context 中运行。

空间可组合
执行与记录

Agent 分析需求、修改代码、运行测试；Session 记录交互和工具调用事件。

Session Event Log
发现错误并重新尝试

测试发现退款逻辑错误。可以从合适的 Session 历史节点 Fork；若文件修改需要撤销，则使用 Workspace 回退机制。

上下文 / 文件回退
替换支付服务

旧支付插件退出并清理注册；新实现进入后，依赖关系重新评估，满足条件的 Agent 可以继续运行。

时间 + 空间可组合
架构意义：系统不再假设运行环境在启动后保持不变，而是允许组件、依赖、上下文和任务分支在运行期间发生变化，并为这些变化建立管理规则。

06 · 常见误区与能力边界

容易误解成更准确的理解
时间可组合就是按时间安排 Agent 任务重点是组件生命周期中的 Effect 如何建立与撤销。
空间可组合就是多机部署重点是 Context 作用域、依赖声明和运行环境变化；不必然涉及物理空间。
依赖注入就是空间可组合的全部依赖注入是重要部分；响应依赖变化、作用域与组件生命周期也很关键。
插件卸载就能撤销插件做过的一切只能撤销被纳入管理且提供清理动作的副作用；外部操作不自动回滚。
Session 回退等于回滚代码Session 管理历史/上下文；代码恢复需要 Workspace 快照、差异或版本控制。
Context 就是安全沙箱Context 是运行时作用域，不应直接视为强安全隔离边界。
生产系统设计提醒：对文件、数据库和外部 API 等有持久影响的动作，必须明确记录边界、失败语义、幂等策略和补偿方案。不要把“可逆 Effect”误认为通用分布式事务。

07 · 一页记住核心概念

概念要回答的问题核心对象主要价值
Temporal Composition什么时候进入、退出？Effect / Disposer动态加载、卸载、清理和热更新
Spatial Composition在哪个环境运行、依赖什么？Context / Dependencies作用域组合、依赖解析、响应式激活
Effect Rollback如何撤销运行时注册？清理函数避免插件残留
Session Rollback如何回到另一条上下文路径？事件历史 / Fork / Replay重新探索执行路径
Workspace Rollback如何撤销文件修改？快照 / Diff / Undo恢复工作区状态
最终心智模型：
时间可组合 = 管好组件的“进与退”；
空间可组合 = 管好组件的“依赖与环境”；
回退 = 明确要恢复的是运行时、会话上下文，还是工作区。
