核心结论

Bacchus 的真正创新，不是单独提出一种新的 LSM Tree，也不是把数据库文件简单搬到对象存储，而是围绕共享存储重新组织数据库的日志、元数据、缓存、Compaction、GC、恢复和资源调度。

它要解决的核心问题是：如何让计算节点不再持有完整的数据副本，同时仍然保持 OLTP 所需的低延迟、高吞吐和可靠性，并让计算、日志、缓存、持久化存储及后台任务能够独立伸缩。
1. PALF / Shared Log将日志能力从计算节点抽离，成为共享服务，是计算节点可重建化的关键。
2. Shared Block Cache把缓存从节点私有资源变成 AZ 级共享资源，缓解对象存储访问延迟。
3. SSLog / 元数据协调统一传播元数据变化，为缓存失效、版本切换和安全回收提供协调基础。
4. 后台任务服务化将 Compaction、GC 等工作从前台计算路径剥离，减少资源竞争。

论文：OceanBase Bacchus: A High-Performance and Scalable Cloud-Native Shared Storage Architecture for Multi-Cloud，arXiv:2602.23571。

一、OceanBase 为什么要做 Bacchus

1.1 传统 Shared-Nothing 架构的结构性约束

传统分布式数据库以节点为资源组织单元。每个 Observer 同时承担计算、日志、数据存储、缓存和部分后台维护工作，数据通过多副本复制保证可靠性。

Observer A计算 + 日志 + 数据 + 缓存
Observer B计算 + 日志 + 数据 + 缓存
Observer C计算 + 日志 + 数据 + 缓存

节点既是计算单元，也是数据副本和运维管理单元。

  • 存储成本：100TB 逻辑数据采用三副本，数据库层需要约300TB物理存储，尚未计入额外空间。
  • 弹性受限：扩容计算节点往往伴随数据迁移、副本构建、日志同步和缓存重建。
  • 冷热数据成本不匹配：历史数据访问频率低，却长期占用高性能云盘。

1.2 为什么不能简单地把云盘换成对象存储

对象存储容量便宜、弹性大，但更适合对象级读写和批量访问，不适合数据库高频随机小 I/O。对象存储的访问延迟、请求粒度和 IOPS 特征，与 OLTP 的要求存在明显差异。

维度高性能云盘对象存储
访问延迟较低较高
随机读写适合不适合高频小 I/O
数据修改支持块级原地修改更适合对象级写入、追加与替换
容量成本较高较低
架构命题：不是“如何把数据放到对象存储”，而是“如何让数据库使用对象存储，同时尽量不让前台事务感知其高延迟”。

1.3 为什么采用 LSM Tree 路径

LSM Tree 将更新先写入日志和内存，再生成不可变 SSTable，通过后续合并整理数据。它减少了频繁原地修改数据页的需求，与对象存储的对象级写入模式更契合。

B+ Tree更新通常需要定位并修改已有页面，涉及随机 I/O、页分裂和页面竞争。
LSM Tree先写日志和 MemTable，再生成不可变 SSTable，后续通过 Compaction 合并。

但 LSM Tree 只解决了数据组织与对象存储的适配问题，并没有自动解决多计算节点共享日志、元数据协调和缓存一致性。这些正是 Bacchus 进一步设计的重点。

二、Bacchus 的整体架构：四类资源解耦

从架构视角，可以把 Bacchus 理解为四类独立资源：计算、日志、缓存和持久化存储。后台 Compaction、GC 等任务则作为可调度的服务能力。

“无状态计算”不是说计算节点完全没有本地状态，而是核心数据状态不再依赖某一台计算机器独占保存；本地缓存和必要状态可以通过恢复流程重建。

三、核心创新一：Shared Service-Oriented Logging

3.1 日志为什么成为存算分离的关键

事务提交需要可靠日志。若所有计算节点直接向对象存储写高频小日志，会遇到延迟高、请求碎片化、写入顺序协调复杂等问题；若仍在每个计算节点维护完整日志副本，又会削弱存算分离的资源收益。

3.2 PALF：把日志能力变成独立服务

PALF（Paxos-backed Append-only Log File system）是基于 Paxos 的追加式日志文件系统。Bacchus 将日志持久化和副本一致性能力从计算节点中抽离，由独立 LogServer 承载。

RW Compute Nodes各 Log Stream 的写入 Leader
↕
PALF Log ServiceLogServer · 日志持久化 · Paxos 共识
Replica 1
Replica 2
Replica 3
↕
RO Compute Nodes拉取日志并 Replay

关键不是 Paxos 本身，而是将日志服务化，使计算节点能够共享可靠日志，而不必各自维护完整的数据副本。

3.3 Sharded Single-Writer，而不是 Multi-Writer

Bacchus 将数据划分为多个 Log Stream。每个 Log Stream 对应一组逻辑数据分区（例如若干 Tablet），同一 Log Stream 只有一个 Leader 负责写入；不同 Log Stream 可以由不同节点并行写入。

Log Stream管理数据Leader
LS-1Tablet 1、2Node A
LS-2Tablet 3、4Node B
LS-3Tablet 5、6Node C
设计思想：不追求多个节点并发修改同一条日志，而是先按 Log Stream 切分写入权，再让不同分片并行工作。这样既保留单流顺序，又获得整体并行度。

3.4 本地日志缓存与共享日志归档协同

Bacchus 并非每次事务提交都直接等待远端对象存储。计算节点保留本地云盘作为日志的非易失缓存，前台日志处理走低延迟路径；历史日志再归档到共享日志服务。其他节点可消费本地可用日志，在需要时从共享日志服务读取。

  1. 事务生成 CLog。
  2. 通过日志持久化与复制机制保障可靠性。
  3. Leader 将历史 CLog 归档到共享日志服务。
  4. 确认迁移和消费位置允许后，回收本地日志。
  5. RO 节点统一消费日志并 Replay。

PALF 内部还使用 Batch 和 Pipeline：Batch 聚合多条日志以降低共识通信开销；Pipeline 允许多批日志流水执行，提高吞吐。

3.5 SSLog：共享元数据日志

数据库除了业务数据，还有 Tablet/SSTable 映射、Schema、分区变化、Compaction 状态、版本信息等元数据。频繁将这些小变更直接写入对象存储会造成大量小 I/O。

SSLog 可以理解为专门用于元数据变化的共享日志，记录 KV 形式的元数据变更。相关节点消费 SSLog，更新本地元数据视图，并据此触发版本更新或缓存失效。

PALF 不只是事务日志基础设施；结合 SSLog，它还成为共享存储架构中元数据变化传播和协调的重要基础。

层次区分：PALF 的 Paxos 共识解决日志服务副本间一致性；Log Stream 的 Leader 机制解决数据库分区写入协调。两者属于不同层次。

四、核心创新二：Shared Block Cache Service

4.1 为什么仅有本地缓存不够

如果十个计算节点都缓存同一批热点数据，可能重复占用大量云盘容量。扩容、故障切换和节点迁移时，也需要重新加载缓存，导致恢复慢、性能抖动。

4.2 多级缓存体系

L1：计算节点内存Micro-block · 最热点数据
↓
L2：计算节点本地云盘Micro-block · 热数据与局部缓存
↓
L3：AZ 共享缓存Macro-block · BlockServer
↓
Object Storage全量持久化数据
层级位置粒度作用
L1计算节点内存Micro-block最热点数据
L2计算节点本地云盘Micro-block热数据、节点局部缓存
L3AZ 共享缓存Macro-block温数据、跨节点复用
后端对象存储SSTable / Macro-block全量持久化

共享缓存由独立 BlockServer 集群实现，使用本地云盘作为缓存介质。同一 AZ 内的 RW、RO 节点共享访问。它是 Read-only Cache，不是事务写入的权威存储，也不是完整数据副本。

4.3 缓存一致性：SSLog + Version-based Invalidation

假设 Node A 正在读取旧 Macro-block，Node B 完成 Compaction 并产生新 SSTable。若 BlockServer 仍提供旧版本，Node A 可能读取过期数据。Bacchus 将元数据版本变化通过 SSLog 传播，并利用版本校验识别缓存失效。

  1. Compaction 或其他操作产生新数据版本。
  2. 元数据变化写入 SSLog。
  3. RW、RO 节点消费 SSLog，感知版本变化。
  4. 缓存条目进行版本校验。
  5. 版本不匹配时，旧缓存不能继续使用，需要刷新。
设计原则：缓存一致性尽量复用共享日志和元数据传播机制，而不是再造一套复杂的全局同步系统。

4.4 Cache Warming：不只复制数据，也复制访问行为

场景预热策略
Major 版本切换预加载新版本热点 Macro-block
Leader / Follower 切换同步 Leader 访问序列，Follower 提前加载 Micro-block
副本迁移通过共享缓存获取数据并迁移热点数据
本地云盘扩缩容调整 ARC 缓存及历史列表

Leader/Follower 预热的价值在于：缓存命中率不仅取决于容量，也取决于缓存内容是否匹配业务访问模式。同步访问序列相当于复制一部分访问行为。

五、核心创新三：重新设计数据持久化与 Compaction

5.1 为什么传统 Dump / Compaction 不够

在 Bacchus 中，数据落盘不仅影响内存释放，还影响日志回收、节点恢复、副本加载和弹性扩容。若大量数据长期停留在 MemTable 对应的日志中，故障恢复就需要 Replay 更多日志。

5.2 Micro Compaction：提前形成小型 SSTable

Bacchus 引入 Micro SSTable。它不是等 MemTable 完全冻结后才持久化，而是在更早阶段将部分数据形成小型 SSTable，并先放在计算节点本地磁盘缓存，后续再上传对象存储。

MemTable增量数据
↓
Micro SSTable提前持久化
Mini SSTableMemTable 冻结后生成
↓
Minor SSTable合并增量数据

Micro SSTable 的价值不仅是提高写入吞吐，更重要的是更早推进数据持久化和 Checkpoint，减少故障恢复时需要 Replay 的日志量。

5.3 Minor Compaction：Macro-block 复用

假设原始 SSTable 有100个 Macro-block，其中只有10个发生变化。若 Compaction 每次都重写100个块，会产生不必要的写放大。通过复用未变化的 Macro-block，只为变化部分写入新块，可以降低对象存储写入量、数据搬运、网络带宽和存储请求成本。

论文还描述了 SSWriter 机制：在指定 Log Stream 等作用域内，由 Leader 选择一个副本承担对象存储写任务，并通过 Lease 控制有效写入权，避免多个副本并发更新相同逻辑数据。

5.4 Major Compaction：从前台计算节点卸载

传统数据库中 Compaction 与前台事务争用 CPU、内存和 I/O。Bacchus 将 Major Compaction 主要放到共享存储层执行，并支持在资源不足或有空闲计算节点时进行 Compaction Offloading。

  1. Root Service 发起 Major Compaction。
  2. Leader 按 Tablet 划分任务并发布调度信息。
  3. 共享存储层执行节点读取相关 SSTable 并合并。
  4. 新版本 SSTable 写入对象存储，元数据随之更新。
  5. 计算节点通过 SSLog 感知新版本，更新本地引用。
  6. 执行缓存预热和 CRC 校验，确认后释放任务资源。
核心变化：前台事务计算与后台数据整理使用不同资源池。Compaction 不再必须绑定在前台数据库节点上。

六、元数据与 GC：共享存储下的全局协调

6.1 元数据分层管理

Bacchus 按 Node、Tenant、Log Stream、Tablet 等层级组织元数据，并区分节点私有元数据和共享元数据。系统层级与用户租户层级承担不同职责，避免所有元数据都依赖一个庞大的全局索引。

元数据层级策略原因
Log Stream 及以上Write-through更新频率较低，强调及时共享
Tablet 及以下Write-back版本较多、更新更频繁

6.2 为什么 GC 在共享存储下更危险

Node A 可能正在读取某个 SSTable，Node B 认为该文件已过期，Node C 仍持有旧版本元数据，长事务也可能需要历史版本。直接删除可能导致仍在使用的数据不可访问。

Bacchus 通过 GC Coordinator、Lease、最小读取 SCN（min_read_scn）、日志 Replay 位置和分阶段删除来协调。

  1. 每个 Log Stream 选举 GC Coordinator。
  2. Coordinator 获取有期限的 Lease。
  3. 收集相关节点的最小读取 SCN 和最小 Replay 位置。
  4. 判断日志和 SSTable 是否已经安全可回收。
  5. 先将删除意图写入 SSLog，让其他节点感知。
  6. 确认安全后执行实际删除并更新元数据。
GC 不是简单的文件清理，而是跨节点、跨事务、跨版本的安全协调。共享存储并不意味着可以无协调地删除数据。

七、一笔事务在 Bacchus 中经历什么

7.1 前台事务

  1. SQL 到达 RW 节点，定位数据所属 Tablet。
  2. 读取优先访问内存和本地缓存；必要时访问 AZ 共享缓存。
  3. 更新产生 CLog，通过相应日志机制保障持久性。
  4. 新数据进入 MemTable。
  5. 事务完成提交。前台不必等待完整 SSTable 合并，也不必每次更新都直接写对象存储。

7.3 RO 节点如何看到最新数据

RO 节点不需要从 RW 节点复制完整数据库，而是从 PALF 获取 CLog 并 Replay，从 SSLog 获取元数据变化，发现新 SSTable 后读取共享对象存储，并利用 Shared Block Cache 复用温数据。

传统节点间数据复制，转变为：共享日志同步 + 共享元数据同步 + 共享数据引用 + 局部缓存构建。

九、OceanBase 构建 Bacchus 的大逻辑

9.1 从节点资源绑定转向云资源池化

传统数据库以节点作为资源单元，CPU、内存、磁盘、日志、缓存和后台任务绑定。Bacchus 将 Compute、Log、Cache、Storage 拆成可独立配置的资源池。

传统模式CPU + Memory + Disk + Log + Cache 绑定在数据库节点上，通常整体扩缩容。
BacchusCompute / Log / Cache / Storage 分别伸缩，后台任务也可调度到独立资源。

9.2 从数据库内部功能转向独立服务能力

原有耦合能力服务化方向
本地日志管理PALF Shared Log Service
节点本地缓存Shared Block Cache Service
元数据变更传播SSLog + Metadata Service
CompactionShared Storage Background Service
垃圾回收全局协调的 GC Service

这些服务并非彼此孤立：PALF 提供共享日志，SSLog 传播元数据，缓存复用版本信息进行失效，Compaction 发布新版本，GC 利用全局状态安全删除。它们构成一个协作体系。

9.3 从数据库副本可靠性转向存储服务可靠性

传统架构通过数据库维护多份完整数据副本。Bacchus 将数据持久性更多交给对象存储，将日志一致性交给 PALF，将计算节点恢复交给日志 Replay 和共享数据重建，将缓存恢复交给本地云盘与共享缓存。

本质：可靠性边界重新划分。不是数据库不再需要高可用，而是数据、日志、计算和缓存分别由不同层承担相应的可靠性责任。

十、架构边界与需要警惕的问题

10.1 Multi-Cloud 不等于跨云多活

能力论文所展示的情况
适配 AWS S3、Alibaba OSS、Azure Blob、MinIO 等明确支持
不同云环境独立部署明确支持
跨云迁移架构有基础，但论文未充分展示完整迁移流程
跨云实时同步与多活论文没有证明
跨云统一日志共识论文没有证明

更准确地说，Bacchus 展示的是 Multi-Cloud Deployment，而不是已经实现跨云统一分布式数据库集群。

10.2 PALF 可能成为新的性能约束点

  • 单个 Log Stream 只有一个写 Leader，热点流是否会成为瓶颈？
  • 日志服务扩容时如何重新分布 Log Stream？
  • LogServer 故障、网络分区时恢复时间如何？
  • 计算节点与日志服务之间的网络延迟对提交延迟有多大影响？

Shared Log 并没有消除日志协调，而是把日志协调从计算节点内部转移到独立服务层。

10.3 Shared Block Cache 可能形成新的热点

  • 热门 Macro-block 是否造成 BlockServer 热点？
  • 共享缓存的网络带宽是否足够？
  • BlockServer 故障后如何恢复？
  • 多租户之间如何隔离缓存资源和淘汰行为？

10.4 对象存储并非所有负载都更便宜

如果全量数据都经常访问、随机读频繁、缓存命中率低、Compaction 很重，缓存、网络和对象存储请求成本可能抵消部分容量成本优势。Bacchus 更适合具有明显冷热分布、可由多级缓存吸收热点访问的工作负载。

Bacchus 并不是简单复制 Socrates。其路径更突出 LSM Tree、对象存储、服务化共享日志和 AZ 级共享块缓存的组合。它通过缓存和后台服务屏蔽对象存储的性能劣势。

十二、总结：应该记住的五个核心思想

  1. 数据与计算分离：计算节点不再持有完整数据副本，成为可快速恢复和扩缩容的执行单元。
  2. 日志与计算分离：PALF 作为独立共享日志服务，解决共享存储下事务日志的共享、持久化和一致性。
  3. 缓存与计算分离：AZ 级 Shared Block Cache 让多个计算节点共享温数据，减少冗余并降低扩容成本。
  4. 前台与后台分离：Micro Compaction、Major Compaction Offloading 等机制，将数据整理从前台事务中剥离。
  5. 数据可靠性与数据库副本解耦：对象存储承担数据持久化，PALF 承担日志复制与一致性，减少数据库自身维护的完整数据副本。
最终判断：Bacchus 是一次面向公有云环境的数据库存储架构重构。它的核心价值在于把 LSM Tree、对象存储、共享日志、共享缓存、元数据协调和后台任务服务化重新组合成一个完整系统，而不是某个孤立算法的突破。
