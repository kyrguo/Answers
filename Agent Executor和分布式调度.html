核心结论先行

这几个项目并不是简单的竞品关系。它们处在相邻但不同的抽象层：通用分布式计算引擎负责“算力如何分布式运行”，Agent Executor 负责“一个 Agent 如何作为长期、可恢复的逻辑执行实体运行”。

Agent 分布式执行底座。重点是 Environment / Runtime 的创建、调度、路由、隔离、生命周期和恢复。

通用分布式计算框架。以 Task、Actor、Object 等抽象承载分布式 AI 与 Python 工作负载。

General compute

一句话概括：Ray / openYuanrong 解决分布式计算基础问题；Google AX / 华为 Agent DX 则把 Agent 的长生命周期、状态恢复、隔离和执行环境管理提升为运行时原生能力。

一、Google Agent Executor 究竟是什么？

Google Agent Executor（AX）被定位为面向 Agent 执行、恢复和分布式部署的开放运行时。它关注的不是 Agent 如何思考，而是 Agent 的执行如何在复杂基础设施条件下可靠地持续运行。

传统 Agent 通常由一个进程承载执行循环、上下文和工具调用状态。任务一旦持续数小时、跨越人工审批、网络中断或机器故障，应用就必须自行处理大量恢复逻辑。AX 试图把这些能力沉淀到 Runtime。

典型场景：长时间运行的 Coding Agent

接收任务并分析代码仓库

模型推理、读取文件、理解项目结构。

创建沙箱并执行代码

安装依赖、修改文件、运行测试。

等待外部事件

等待测试结果、用户反馈或人工审批，可能持续很久。

恢复并继续执行

从已保存的状态继续，而不是从头开始。

提交结果或创建执行分支

可以沿原路径继续，也可以从某个检查点探索其他方案。

AX 关注的关键能力

能力含义解决的问题
Durable Execution持久化执行状态与事件进程或节点故障后，任务仍可恢复
Secure Isolation隔离 Agent、工具和执行环境降低不可信代码、多租户执行的风险
Session Consistency维护会话状态写入一致性避免多个执行者并发修改同一 Session
Connection Recovery断线后按事件位置重新连接客户端连接中断不意味着任务丢失
Trajectory Branching从 Checkpoint 派生执行轨迹复用已有进度，尝试不同执行路径
关键理解：AX 不只是“把 Agent 分发到多台机器执行”。它更重要的价值，是把 Agent 执行过程变成可记录、可恢复、可管理的运行时对象。

二、为什么 Durable Execution 是核心？

Durable Execution 可以理解为：程序的执行进度不再只存在于进程内存中，而是通过事件日志、快照等机制持久化。进程退出后，运行时可以根据持久化信息重建执行状态。

传统执行方式

Agent Process上下文、工具状态和执行进度主要在内存中
↓
模型 → 工具 → 结果 → 下一步
↓
进程崩溃状态丢失，应用需要自行补救

持久化执行方式

Agent / Tool / Skill / Sandbox逻辑执行单元
↓
Event Log记录发生了什么
Snapshot保存某时刻状态
↓
Recovery恢复状态并继续执行

三个概念要分清

  • Event Log：记录执行过程中发生的事件，例如工具调用开始、工具结果返回、审批通过等。
  • Snapshot：保存某个时点的状态，避免每次恢复都从最早事件开始重放。
  • Recovery：读取快照并应用后续事件，重建可继续执行的状态。
容易被低估的难点：恢复 Agent 不等于重新调用一次 LLM。必须判断工具调用是否已经成功、外部副作用是否发生、重试是否会造成重复操作。这涉及幂等性、事件确认和状态一致性。

因此，Durable Execution 与数据库领域的 Event Sourcing、Checkpoint / Recovery 有相通之处，但 Agent 场景还要额外处理模型调用和外部工具的非确定性、副作用与长时间等待。

三、华为 Agent DX 是不是同一类东西？

华为 openJiuwen 生态中的 Agent DX（Agent Distributed eXecutor）与 Google AX 属于同一大方向：都试图为 Agent 提供专用的分布式执行基础设施。但二者公开架构的侧重点不同。

核心定位：Agent Framework 负责 Agent 的业务逻辑与思考过程；Agent DX 负责 Agent 执行环境的创建、调度、路由、隔离和生命周期管理。

Agent DX 的职责拆分

组件 / 概念主要职责
Agent Template / Binding定义 Agent 模板，以及模板与运行实例之间的绑定关系。
Environment描述 Agent 所需的执行环境，是环境管理的重要抽象。
Coordinator / Scheduler协调请求、分配资源、选择执行位置。
sandboxd创建和管理隔离执行环境，承接沙箱相关能力。
Execd在执行环境内提供命令、文件、终端、端口等操作能力。
Checkpoint / Shared Storage保存恢复所需状态，并支持跨节点恢复。

一个 Agent 执行代码时，Agent DX 做什么？

Agent Framework 决定执行代码

例如模型生成了一段 Python 代码，需要调用工具运行。

Agent DX 接收环境请求

通过 Environment API / SDK 请求创建或使用执行环境。

调度器选择计算节点

根据资源与环境状态，选择合适的执行位置。

sandboxd 创建隔离环境

准备沙箱，Execd 在其中执行命令。

运行时管理状态和生命周期

处理请求路由、环境状态、暂停与恢复等。

上述对比描述的是公开架构的重心，不意味着两者能力边界完全互斥。两边都涉及执行环境、Checkpoint 和恢复。

版本演进方面，早期 Agent DX 资料更强调通过 openYuanrong 的 meta_service 注册 Agent、通过 frontend 调用 Agent；当前项目主线则呈现出 Coordinator、Environment、sandboxd、Execd 等更完整的分布式执行平台结构。分析时应以对应版本的仓库和文档为准。

四、openYuanrong 与 Ray 是同类东西吗？

基本可以归为同一大类：通用分布式计算运行时 / 框架。它们提供编程抽象、分布式调度和数据共享能力，让原本在单机执行的程序能够扩展到集群。

五、Agent Executor 与 Ray 到底是什么关系？

最关键的区分是：Ray 主要回答“计算如何分布式运行”；Agent Executor 主要回答“Agent 作为一个长期逻辑执行实体，如何被创建、暂停、恢复、隔离和管理”。

一个 Ray Actor 有状态，但不等于完整的 Durable Execution

例如，Ray Actor 可以在内存中维护 Agent 的对话历史、运行变量和中间结果：

class Agent:
    def __init__(self):
        self.history = []

    def execute(self, task):
        self.history.append(task)

这说明 Actor 可以有状态，但如果承载 Actor 的节点宕机，系统还需要回答更多问题：

  • Actor 的状态是否有持久化副本？如何恢复？
  • 执行进度具体到了哪一步？
  • 上一次工具调用是否已经成功？
  • 重试会不会重复扣款、发邮件或修改外部系统？
  • 如果 Agent 正在等待人工审批，如何跨进程、跨节点继续？

这些不是“有 Actor”就自动具备的能力。需要专门的持久化执行协议、事件记录、Checkpoint、幂等控制和恢复机制。

Google 的 AX 与 Agent Substrate：两个相邻层次

Google 公开介绍中还提出了 Agent Substrate。它与 AX 的关系，有助于理解 Agent Runtime 和计算基础设施之间的边界。

Agent / Harness / Skills / ToolsLangGraph、ADK、自定义 Agent 等
↓
Agent Executor（AX）执行语义、持久化执行、Session 一致性、Checkpoint / Recovery、轨迹分支
↓
Agent SubstrateAgent 优先的计算基础设施：Worker Pool、Sandbox、资源弹性与执行环境管理
↓
Kubernetes / 计算节点CPU、Memory、GPU、网络与存储等基础资源

可以这样理解：

  • Agent Executor：关心 Agent 执行过程的语义与可靠性。
  • Agent Substrate：关心 Agent 在哪里运行、使用什么资源、如何获得隔离环境。
  • Kubernetes：提供更底层的容器编排和集群基础设施。

因此，AX 并不等于 Ray，也不意味着 AX 必须运行在 Ray 之上。Google 的公开路线是 AX 与 Agent Substrate 配合，由后者提供面向 Agent 的计算基础设施。

七、为什么需要 Agent 专用执行层？Ray / openYuanrong 不够吗？

Agent 正在成为一种不同于传统在线服务和批处理任务的计算负载。

传统负载典型特征Agent 负载的不同之处
在线服务进程长期运行，持续处理请求Agent 的一次任务可能跨越很长时间，期间多次等待外部事件
批处理任务提交、执行、结束，输入输出相对明确Agent 执行路径动态变化，可能反复规划、调用工具和请求人工决策
普通 Actor持有状态并处理消息Agent 还需要执行轨迹、外部副作用、会话一致性和可恢复语义

Agent 生命周期示意

启动

创建 Agent 实例，加载上下文、工具和运行配置。

思考与执行

调用模型、执行工具、产生中间状态。

等待

等待用户、外部 API、审批或异步事件，可能持续数小时。

恢复

重新加载状态，继续之前的任务。

继续或分支

沿原路径继续，或基于 Checkpoint 探索不同路径。

休眠或结束

释放计算资源，保留必要状态，等待后续唤醒或完成清理。

Agent-Native Runtime 要解决的资源问题

Agent 可能大部分时间处于等待状态，真正消耗 CPU 的时间只占一小部分。如果一个 Agent 长期绑定完整容器，资源利用率可能很低。因此新一代执行基础设施会重点考虑：

  • 计算与状态分离：Agent 不活跃时释放计算资源，保留逻辑状态。
  • 快速唤醒：新事件到来时，尽快恢复到可执行状态。
  • 细粒度隔离：不同用户、不同 Agent 的执行环境相互隔离。
  • 状态可迁移：Agent 能够在不同计算节点间恢复或迁移。
  • 执行可恢复：节点故障或网络中断不应导致长任务必然从头开始。
架构演进方向：
从“一个 Agent = 一个长期运行的进程 / 容器”，走向“一个 Agent = 一个可持久化、可暂停、可恢复、可迁移的逻辑执行实体”。计算资源成为它按需占用的执行载体。

八、架构趋势与最终判断

未来可能形成的三层结构

层次主要职责代表项目
Agent Harness / FrameworkAgent 如何思考、规划、调用工具ADK、LangGraph、openJiuwen
Agent Execution RuntimeAgent 如何持久执行、暂停、恢复、隔离、管理会话Google AX、Huawei Agent DX
Distributed Compute Runtime如何提供分布式算力、资源调度和数据传输Ray、openYuanrong

趋势一：Agent Runtime 从 Framework 中独立出来

过去 Agent Framework 往往把执行循环、状态管理、工具调用和运行环境放在一起。未来企业可能运行多种 Agent Framework，但统一交给一个 Agent Execution Runtime 管理。这样更换 LangGraph、ADK 或其他 Harness 时，不必重建整套执行基础设施。

趋势二：通用分布式计算平台增加 Agent 专用能力

Ray 和 openYuanrong 不需要重新发明通用分布式计算系统，而可以在已有能力上增加 Agent Session 管理、Durable Execution、Checkpoint / Recovery、Sandbox 隔离、Agent 级资源调度，以及计算与状态分离。

一个值得深入研究的架构问题：状态应该由谁管理？

路线 A：Agent Executor 管理状态

底层计算引擎保持通用。Agent Runtime 通过 Event Log、Snapshot、Checkpoint 等机制实现恢复。优势是层次清晰、后端可替换；代价是状态协议和执行语义需要在 Runtime 层实现。

路线 B：底层计算引擎深度管理状态

把 Actor 生命周期、内存数据、调度和状态迁移更紧密地结合。潜在优势是减少跨层开销、提升资源利用效率；代价是计算引擎与 Agent 语义耦合更深。

两条路线并非完全对立，也可能形成混合架构。关键在于状态所有权、持久化边界、故障恢复协议和外部副作用的处理方式。

对华为路线的判断
openYuanrong 已具备函数生命周期管理、休眠唤醒、跨节点迁移和分布式数据系统等基础能力。若能将这些通用 Serverless 执行能力，与 Agent DX 的 Environment、Agent 生命周期和恢复语义深度结合，就有机会形成真正的 Agent-Native Runtime。其价值不只是给 Agent 套一层分布式调度 API，而是把 Agent 的逻辑生命周期与底层计算资源管理协同起来。
